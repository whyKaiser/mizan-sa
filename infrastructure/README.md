# إعداد الخدمة السحابية

هذه تعليمات إكمال، وليست إعلانًا أن البيئة السحابية مفعلة. لا تُطبّق المخطط على مشروع آخر مستخدم لغرض مختلف.

1. أنشئ مشروع Supabase مخصصًا باسم ميزان بعد اعتماد المؤسسة والتكلفة.
2. نفّذ `schema.sql` في المشروع. لا توجد فيه بيانات شخصية أو كلمات مرور.
3. تحقق من أن RLS مفعلة وأن الزائر `anon` لا يملك صلاحيات جدول المشاريع. السياسات تسمح للمستخدم فقط بصفوف `user_id = auth.uid()`.
4. اضبط Site URL على رابط Pages النهائي، وروابط العودة المسموحة على هذا العنوان بالضبط؛ أضف localhost للتطوير عند الحاجة فقط.
5. فعّل تأكيد البريد وكلمة مرور قوية. اضبط مزود SMTP موثوقًا باسم المرسل «ميزان». بريد Supabase الافتراضي مقيد بعناوين فريق المؤسسة ولا يصلح لتسجيل عامة المستخدمين.
6. انسخ عنوان الخدمة ومفتاح Publishable العام إلى `src/config.js`. لا تنسخ أي Secret Key أو service_role إلى الواجهة.
7. أعد البناء والنشر ثم اختبر حسابين تجريبيين مستقلين: إنشاء مشروع في A؛ عدم ظهوره لحساب B؛ رفض B لقراءة/تعديل/حذف معرف مشروع A؛ منع إضافة صف باسم مالك آخر.
8. اختبر تسجيل الدخول بكلمة مرور خاطئة، تأكيد البريد، استعادة كلمة المرور، الخروج، العودة من جهاز آخر، وتعارض تحديث نسختين.
9. شغّل مستشار الأمان والأداء، ووثّق النتائج الفعلية قبل تغيير حالة الجاهزية في README والدليل.

الحفظ السحابي لا يخزن كلمة المرور في جدول المشروع. الاسم الكامل للعرض في بيانات المستخدم لا يمنح أي صلاحيات. قيود JSONB تمنع حمولة ضخمة وهوية مشروع مخالفة؛ لا تجعل حسابات المستخدم سجلات محاسبية معتمدة.

المخطط قابل لإعادة التطبيق دون حذف المشاريع؛ يعيد تعريف سياسات هذا الجدول. عند الانتقال إلى تطوير جماعي منتظم، أدر التغييرات عبر Supabase CLI ومراجعة migrations.

المراجع: [إرسال البريد](https://supabase.com/docs/guides/auth/auth-smtp)، [أمان الصفوف](https://supabase.com/docs/guides/database/postgres/row-level-security).
