# خريطة المذاكرة
## مسار القراءة
ابدئي بالمشكلة والهدف وحدود المشروع، ثم رحلة المستخدم. افهمي فصل التخطيط عن المحاكي قبل دراسة المعادلات والقيود.
بعد الجانب المحاسبي، اقرئي بنية الملفات وتدفق البيانات والبرمجة غير المتزامنة والحفظ والأمان. أخيرًا طبّقي سيناريو العرض وأسئلة المناقشة.
## محاور الدليل
المشكلة والهدف؛ المتطلبات والهوية؛ رحلة المستخدم؛ الأدوات والبنية؛ البيانات والأحداث؛ قواعد الحساب؛ مثال التخطيط؛ نقطة التعادل وماذا لو؛ القيد المزدوج؛ المحاكي والقوائم؛ الحفظ والحسابات؛ الأمان؛ الاختبارات؛ التشغيل والنشر؛ نقل الملكية؛ العرض؛ أسئلة المناقشة؛ التمارين؛ الحدود والمراجع.
## ما الذي يجب أن تتقنه كل طالبة؟
شرح المنصة في دقيقة، إنشاء مشروع دون مساعدة، حساب ربحه يدويًا، تمييز المدين والدائن، الوصول إلى الملفات المسؤولة، وشرح حدود المشروع بصراحة.
يجوز توزيع التعمق بين أعضاء الفريق، لكن لا تجعلوا كل طالبة تعرف شاشة واحدة فقط؛ أسئلة المناقشة قد تربط الواجهة بالمحاسبة وقاعدة البيانات.
## قاعدة إجابة مفيدة
ابدئي بالوظيفة، ثم اسم الملف أو الدالة، ثم مثال رقمي، ثم حد أو حالة استثنائية. مثال: دالة calculate تحسب التعادل؛ 8000 ÷ 20 = 400 وحدة؛ إذا لم يغطِّ السعر تكلفة الوحدة فالتعادل غير ممكن بهذه الفرضيات.

# المشكلة والهدف والقيمة
## المشكلة
قد يملك صاحب مشروع صغير فكرة جيدة دون تصور واضح للتكاليف والمبيعات اللازمة لتغطيتها. تتفرق الأرقام بين أوراق أو حاسبات، ويصعب فهم أثر تغيير السعر أو ربط العمليات اليومية بالقوائم المالية.
للطالبات، حفظ تعريف المدين والدائن دون رؤية الأثر على النقدية والمخزون والالتزامات يجعل التعلم نظريًا. ميزان يربط الإدخال والعملية والنتيجة في تجربة واحدة.
## الهدف العام
بناء منصة ويب عربية تعليمية تساعد المستخدم على تخطيط مشروع بسيط، تحليل الربح والتعادل، تجربة بدائل، ومحاكاة عمليات محاسبية مع قيود وقوائم تتحدث بحسب البيانات المسجلة.
## أهداف قابلة للتحقق
يستطيع المستخدم إنشاء عدة مشاريع مستقلة، وإدخال تكاليف ثابتة ومتغيرة، والحصول على حسابات صحيحة، وإضافة عمليات متوازنة، وحفظ البيانات وإعادة فتحها، وطباعة تقرير واضح.
يقاس نجاح التنفيذ باختبارات المعادلات والحفظ وتدفق الواجهات، لا بادعاء تحسن أرباح مستخدمين حقيقيين. لم تُنفَّذ دراسة ميدانية على طلاب أو أصحاب مشاريع في هذه النسخة.
## الفئة المستهدفة
طلاب المحاسبة وريادة الأعمال وأصحاب الأفكار الصغيرة في مرحلة التعلم والدراسة الأولية. المنصة ليست بديلًا عن نظام محاسبي معتمد أو محاسب مهني.

# المتطلبات وحدود النطاق
## وظيفية
البداية وتسجيل الدخول وإنشاء الحساب والزائر؛ تغيير كلمة المرور بمعرفة الحالية؛ إدارة مشاريع متعددة؛ التكاليف والإيرادات والنتائج؛ نقطة التعادل وماذا لو؛ ثمانية أنواع عمليات؛ سجل وتفاصيل القيود؛ قائمة دخل وميزانية؛ تقارير محفوظة وطباعة؛ إعدادات شخصية ومظهر وأرقام وإشعارات داخلية. استعادة كلمة المرور بالبريد غير متاحة.
## غير وظيفية
واجهة عربية من اليمين إلى اليسار، مناسبة للجوال والحاسوب، رسائل خطأ مفهومة، رفض القيم غير الصالحة، حماية مشاريع الحسابات بسياسات ملكية، وإمكانية بناء النسخة واختبارها من المصدر.
## تحويل الصورة إلى منصة
الصورة مرجع للهوية وتسلسل الشاشات، وليست برنامجًا جاهزًا. التنفيذ يستخدم بطاقات وألوانًا وأيقونات قريبة من المرجع، وشريطًا جانبيًا للحاسوب وتنقلًا سفليًا للجوال. لذلك ليس نسخًا بكسلًا مقابل بكسل لصورة الهواتف.
لم تُنسخ الأخطاء الرقمية في الرسم. مثلًا: 10000 ÷ (25 - 15) تساوي 1000، لا 400. صحة الحساب مقدمة على مطابقة رقم خاطئ بالصورة.
## حدود محاسبية مهمة
التخطيط لمنتج أو خدمة واحدة داخل كل مشروع، وبأفق شهري. لا ضريبة قيمة مضافة ولا زكاة ولا إهلاك تلقائي ولا رواتب تفصيلية ولا ربط بنكي أو فواتير إلكترونية معتمدة. القوائم التعليمية تعكس ما أدخله المستخدم فقط.

# رحلة المستخدم والواجهات
## من الفكرة إلى دراسة مالية
شاشة الشعار ثم الترحيب. يختار المستخدم حسابًا أو وضع الزائر، ثم إنشاء مشروع ونوعه، واسمًا ورأس مال ووصفًا. بعد ذلك يضيف الثابت شهريًا والمتغير لكل وحدة، ثم اسم المنتج والسعر والكمية الشهرية.
عند حساب النتائج تظهر الإيرادات والتكاليف والربح والهامش والتعادل ومقارنة بصرية. يستطيع المستخدم تعديل بياناته أو تجربة سيناريو دون تغيير المشروع الأصلي.
## من العملية إلى القوائم
يفتح المحاكي، يختار عملية، يُدخل المبلغ والتاريخ والوصف، ويعاين المدين والدائن. بعد التسجيل يظهر القيد في السجل ويُحدَّث ميزان الأصول والالتزامات وحقوق الملكية.
يفتح قائمة الدخل أو الميزانية أو التقرير. حفظ نسخة تقرير يحتفظ بلقطة من أرقام المشروع في ذلك الوقت، بينما التقرير الحالي يتبع آخر تعديل.
## إدارة المشروع
مشروع جديد لا يستبدل القديم. لكل مشروع معرف مستقل. فتح مشروع يعيد بياناته، والتعديل يُحفظ عند الإجراء المناسب. حذف المشروع يحتاج تأكيدًا لأن عملياته وتقاريره تتبعه.
الزائر يحفظ على المتصفح نفسه فقط. الحساب الحقيقي يحفظ في الخدمة السحابية ويمكن فتح مشاريعه من جهاز آخر بعد تسجيل الدخول. إغلاق نافذة خاصة أو مسح بيانات المتصفح قد يمحو بيانات الزائر.

# الأدوات ولماذا اختيرت
## واجهة الويب
HTML يبني الهيكل الدلالي للنماذج والعناوين. CSS يحدد الهوية والتجاوب والطباعة. JavaScript ينفذ الحسابات والأحداث والحفظ. المشروع يستخدم JavaScript مباشرة، وليس React أو تطبيق هاتف أصلي.
الخط Tajawal محلي ضمن البناء عبر حزمة @fontsource/tajawal 5.3.0. الأيقونات والشعار رسومات SVG متجهة؛ لا يحتاج كل رمز إلى صورة خارجية. لتنزيل التقرير مباشرة تستخدم html2canvas 1.4.1 وjsPDF 4.2.1، وتُحمّلان عند طلب PDF فقط.
## البناء والتطوير
Node.js يشغّل أدوات التطوير والاختبارات، ولا يلزم تثبيته عند المستخدم النهائي. npm يدير الحزم. Vite 8.3.1 يشغّل خادم التطوير ويبني ملفات الإنتاج المصغرة. ملف package-lock.json يثبت شجرة الاعتماديات.
Git يتتبع تغييرات الملفات. GitHub يحفظ المستودع ويسهّل التسليم. GitHub Pages يستضيف ملفات الواجهة الثابتة عبر HTTPS، لكنه لا يشغّل PostgreSQL أو خادم حسابات داخل المستودع.
## الخلفية المفعلة
Supabase يوفر Auth وPostgreSQL وواجهة بيانات. مكتبة @supabase/supabase-js 2.117.2 تربط الواجهة بهذه الخدمات. المشروع على خطة Free، والجدول وسياسات الملكية مطبقة ومختبرة بحسابين حقيقيين اصطناعيين. لا يوجد SMTP أو اشتراك بريد؛ التسجيل مباشر ضمن حدود النسخة التعليمية.
## أدوات التحقق والتوثيق
node:test وnode:assert للاختبارات الآلية، وفحص المتصفح للواجهات. هذا الدليل يُولَّد باستخدام Python وReportLab مع دعم تشكيل العربية، ثم يُراجع بعد تحويل صفحاته إلى صور.

# شكل البيانات والحالة
## كائن المشروع
يحمل المشروع id وname وtype وcapital وdescription وproduct وprice وunits، وثلاث مصفوفات: costs وjournal وreports. يحمل أيضًا createdAt وrevision.
id معرف UUID يولد عبر crypto.randomUUID. الاسم قابل للتكرار، لكن المعرف لا يعتمد عليه. revision رقم إصدار للحفظ، لا رقم الإصدار العام للمنصة.
## التكلفة والقيد والتقرير
التكلفة تحتوي id وname وkind وamount. kind إما fixed للمبلغ الشهري أو variable لتكلفة الوحدة، لذلك لا نجمع الاثنين مباشرة قبل ضرب تكلفة الوحدة في عدد الوحدات.
القيد يحتوي id وkind وlabel وamount وdate وnote وlines. كل سطر من lines يحمل account وdebit وcredit. التقرير المحفوظ يضم createdAt ونسخة مستقلة من المشروع دون تضمين سلسلة تقارير داخل تقارير.
## الحالة أثناء التشغيل
user للمستخدم، guest لوضع الزائر، projects لقائمة المشاريع، selected لمعرف المشروع المفتوح، draft للمسودة الجديدة، view للشاشة، وbusy لمنع النقرات المتكررة أثناء الحفظ.
structuredClone ينسخ البيانات قبل تعديلها. لا نحدّث النسخة المعروضة على أنها محفوظة حتى يؤكد مسار التخزين النجاح. هذا يقلل رسائل النجاح الكاذبة وفقدان الحالة عند فشل الطلب.
## سؤال شائع
هل البيانات كلها متغيرات؟ في الذاكرة أثناء التشغيل نعم، لكنها تُكتب إلى localStorage للزائر أو إلى قاعدة البيانات للحساب. الذاكرة وحدها تضيع عند إعادة التحميل.

# الأحداث وتدفق التنفيذ
## كيف يعمل زر؟
زر الواجهة يحمل data-action مثل nav:results. مستمع click واحد يقرأ أقرب عنصر يحمل هذا الوصف، ثم يوجه الطلب إلى action. نموذج يحمل data-form، ويعالجه submit المناسب.
هذا يسمى تفويض الأحداث. يفيد لأن render يستبدل HTML الشاشات؛ لا نحتاج إلى ربط مستمع جديد لكل زر بعد كل إعادة عرض.
## ماذا يحدث عند حفظ معلومات مشروع؟
يُفحص النموذج أولًا، ثم تُقرأ الحقول عبر FormData، وتُنسخ بيانات المشروع، وتُتحقق القيم. تستدعى persist ثم saveProject. بعد نجاح الحفظ تُحدّث القائمة ويُفتح قسم التكاليف.
## عمليات غير متزامنة
async وawait يسمحان بانتظار طلب الخادم. try وcatch يعالجان الفشل. busy يمنع تكرار العملية أثناء الانتظار. epoch يمنع نتيجة تحميل قديمة من استبدال جلسة أحدث.
## التنقل
تعتمد الواجهة أجزاء الرابط مثل #results و#simulator. الجزء الذي يبدأ بعلامة # لا يطلب صفحة مستقلة من GitHub Pages، لذلك يناسب استضافة واجهة ثابتة.
## مقتطف توضيحي مبسّط
```js
async function handleSave(project) {
  try {
    const saved = await saveProject(project, user);
    render(saved);
  } catch (error) {
    showError(error.message);
  }
}
```
هذا نموذج تعليمي للتدفق، وليس نسخًا حرفيًا للدوال في main.js. الأسماء الفعلية الأساسية هي run وsubmit وpersist وrender.

# الحسابات المالية خطوة بخطوة
## المدخلات
السعر P، والعدد الشهري Q، والتكلفة الثابتة F، وتكلفة الوحدة المتغيرة V. رأس المال تمويل متاح، وليس إيراد بيع ولا مصروفًا يطرح تلقائيًا من الربح.
## المعادلات
```text
Revenue = P * Q
Variable total = V * Q
Total cost = F + V * Q
Profit = Revenue - Total cost
Profit margin = Profit / Revenue * 100
Contribution per unit = P - V
```
الهامش هنا نسبة صافي الربح المتوقع إلى الإيراد. ليس هو هامش المساهمة، وليس نسبة الزيادة على التكلفة. عند إيراد صفر نعرض أن الهامش غير معرّف بدل القسمة على صفر.
## الدقة
تحوَّل المبالغ إلى هللات صحيحة باستخدام Math.round(amount * 100)، وتُجرى عمليات الجمع والضرب عليها ثم تعاد إلى ريال. هذا يقلل أخطاء الكسور الثنائية مثل 0.1 + 0.2 في JavaScript.
لا تعني الطريقة دقة بلا حدود؛ لذلك نرفض المجاميع التي تتجاوز Number.isSafeInteger. نرفض القيم السالبة وغير المحدودة والكميات الكسرية والمبالغ الموجبة التي تقرَّب إلى صفر.
## أين الكود؟
number تتحقق من الأرقام، وtext تتحقق من الحقول النصية، وcalculate تطبق الحسابات. الدالة calculate لا تحفظ البيانات ولا تتصل بالشبكة؛ يمكن اختبارها منفصلة.

# مثال التخطيط المعتمد للمذاكرة
## افتراضات واضحة
مشروع طباعة صور؛ رأس المال 20000 ريال؛ سعر الصورة 25 ريال؛ مبيعات 300 صورة شهريًا. التكاليف الثابتة الشهرية 8000 ريال، وتكلفة الورق والحبر والتغليف 5 ريالات لكل صورة.
هذه أرقام تعليمية لا عروض أسعار سوقية. لا تخلطي هذا المثال بأرقام العمليات المسجلة في المحاكي؛ لكل جزء غرض مختلف.
## الحل
```text
Revenue = 25 * 300 = 7500
Variable total = 5 * 300 = 1500
Total cost = 8000 + 1500 = 9500
Profit = 7500 - 9500 = -2000
Margin = -2000 / 7500 * 100 = -26.67%
Contribution = 25 - 5 = 20
Break-even units = 8000 / 20 = 400
```
## التفسير
كل صورة تساهم بعشرين ريالًا في تغطية الثابت بعد تغطية تكلفتها المتغيرة. بيع 300 صورة يحقق مساهمة 6000 فقط، أقل من الثابت 8000، لذلك تظهر خسارة 2000.
عند بيع 400 صورة: الإيراد 10000، والمتغير 2000، وإجمالي التكلفة 10000، والربح صفر. بعد هذه النقطة يزيد الربح مع كل وحدة بشرط ثبات السعر والتكلفة.

المتطلبات الأصلية تذكر «مواد وتغليف 1000» دون تحديد تكلفة الوحدة. يجب تحديد هل هذا إجمالي فترة أم مبلغ لكل وحدة؛ إدخال 1000 في حقل تكلفة الوحدة يضربه في 300، وليس هو المقصود عادةً. جودة المدخلات جزء من صحة النتيجة.

# التعادل وماذا لو؟
## معنى نقطة التعادل
عدد الوحدات الذي يجعل الإيراد يغطي التكاليف في النموذج الخطي الحالي. القانون هو الثابت مقسومًا على مساهمة الوحدة. نستخدم Math.ceil لأن المنتج هنا يباع بوحدات صحيحة.
```js
const contribution = price - variableUnit;
const breakEven = contribution > 0
  ? Math.ceil(fixed / contribution)
  : null;
```
هذا مقتطف مبسط؛ calculate تعالج أيضًا حالة الثابت صفر. إذا كان السعر أقل من أو يساوي تكلفة الوحدة مع وجود ثابت، فلا يوجد تعادل قابل للتحقق بزيادة العدد وحدها.
## سيناريو السعر
في المثال السابق، رفع السعر إلى 30 مع بقاء العدد 300 يجعل الإيراد 9000 والتكلفة 9500 والخسارة 500. التحسن 1500، لكنه ليس ربحًا موجبًا بعد.
## سيناريو السعر والعدد
سعر 30 وعدد 400 يعطي إيرادًا 12000 ومتغيرًا 2000 وإجمالي تكلفة 10000 وربحًا 2000. الفرق عن الخطة الأصلية 4000 ريال.
## عدم تعديل الأصل
واجهة ماذا لو تستدعي calculate ببدائل مؤقتة، ولا تستدعي saveProject. الرجوع للنتائج يعرض الخطة الأصلية. لتحويل السيناريو إلى خطة معتمدة، عدلي شاشة الإيرادات واحفظيها.
## حدود التفسير
رفع السعر لا يضمن ثبات الطلب في الواقع، وقد تزيد التكاليف الثابتة عند توسع الطاقة. ميزان يجيب عن أثر الفرضيات المدخلة، ولا يتنبأ بسلوك السوق.

# القيد المزدوج: الفكرة قبل الحفظ
## القاعدة
لكل عملية أثر متوازن: مجموع المدين يساوي مجموع الدائن. المدين والدائن طرفا تسجيل، وليس المدين دائمًا خسارة أو الدائن دائمًا ربحًا.
الأصول والمصروفات والمسحوبات تزيد عادةً في المدين. الالتزامات ورأس المال والإيرادات تزيد عادةً في الدائن. العكس يخفضها.
## أمثلة تفسيرية
شراء مخزون نقدًا لا يعني تسجيل مصروف تلقائيًا؛ هو استبدال أصل نقدي بأصل مخزون. شراء معدات بالأجل يزيد أصل المعدات والتزام الدائنين.
إضافة رأس مال ليست إيراد مبيعات. مسحوبات المالك تخفض حقوق الملكية وليست مصروف إيجار أو تشغيل. سداد الدائنين يخفض نقدية والتزامًا سبق تسجيله.
## تكلفة البيع
القيد المبسط للبيع: من النقدية إلى الإيرادات. عند إدخال تكلفة البضاعة المباعة، تضيف المنصة قيدًا آخر من تكلفة البضاعة المباعة إلى المخزون. بذلك لا يظهر كامل سعر البيع كصافي ربح إذا كان للمخزون تكلفة.
## القاعدة في الكود
OPERATIONS تربط نوع العملية بالحساب المدين والدائن. transaction تتحقق من العملية والمبلغ والتاريخ والأرصدة، ثم تنشئ lines. ledger تجمع السطور وترفض القيد غير المتوازن.
استخدمي اسم الحساب وسبب تغيره عند الشرح، وليس عبارة «البرنامج اختار هذا الطرف» فقط. يجب أن تستطيعي كتابة القيد دون فتح المنصة.

# العمليات الثماني المدعومة
## الشراء
شراء بضاعة نقدًا: مدين المخزون، دائن النقدية. شراء بضاعة بالأجل: مدين المخزون، دائن الدائنون. شراء معدات بالأجل: مدين المعدات، دائن الدائنون.
## البيع والمصروف
بيع نقدًا: مدين النقدية، دائن الإيرادات. إذا كانت تكلفة البيع معلومة: مدين تكلفة البضاعة المباعة، دائن المخزون بالقيمة المدخلة. دفع مصروف: مدين المصروفات، دائن النقدية.
## التمويل والالتزامات
سداد الدائنين: مدين الدائنون، دائن النقدية. إضافة رأس مال: مدين النقدية، دائن رأس المال. مسحوبات المالك: مدين المسحوبات، دائن النقدية.
## التحقق قبل التسجيل
لا يسمح بدفع نقدي يتجاوز النقدية الحالية، ولا بسداد أكثر من رصيد الدائنين، ولا بتكلفة مبيعات تتجاوز المخزون. يرفض التاريخ غير الصحيح والمبلغ غير الموجب. هذه ضوابط تعليمية لمنع عمليات مستحيلة في النموذج الحالي.
## السجل
التاريخ هو تاريخ العملية المدخل. createdAt وقت تسجيلها تقنيًا. تعرض البطاقة الرقم والنوع والمدين والدائن؛ التفاصيل تضيف المبلغ والتاريخ والشرح والوصف.
لا توفر النسخة الحالية تعديل القيود أو عكسها بعد الحفظ. احتفظي بمشروع مستقل للتجارب الخاطئة؛ لا تصفي السجل بأنه نظام تدقيق محاسبي متكامل أو سجل غير قابل للعبث على الخادم.

# مثال المحاكي الكامل
## رصيد افتتاحي
رأس المال 20000 ريال يبدأ كنقدية مدينة مقابل رأس مال دائن. لا تدخل عملية «إضافة رأس مال 20000» مرة ثانية إلا إن كانت زيادة جديدة فعلًا.
## خمس عمليات
1. شراء بضاعة نقدًا 3000: المخزون مدين والنقدية دائن. 2. شراء معدات بالأجل 5000: المعدات مدين والدائنون دائن.
3. دفع إيجار 1000: المصروفات مدين والنقدية دائن. 4. بيع نقدًا 2500: النقدية مدين والإيرادات دائن. 5. سداد دائنين 1500: الدائنون مدين والنقدية دائن.
## النتائج دون إدخال تكلفة بيع
```text
Cash = 20000 - 3000 - 1000 + 2500 - 1500 = 17000
Inventory = 3000
Equipment = 5000
Assets = 17000 + 3000 + 5000 = 25000
Liabilities = 5000 - 1500 = 3500
Income = 2500 - 1000 = 1500
Equity = 20000 + 1500 = 21500
25000 = 3500 + 21500
```
## ماذا لو كانت تكلفة البضاعة المباعة 1200؟
تُسجَّل مع البيع: يصبح المخزون 1800، وصافي الدخل 300، والأصول 23800، وحقوق الملكية 20300. المعادلة تبقى متوازنة: 23800 = 3500 + 20300.
غياب تكلفة البيع لا يعني أنها صفر اقتصاديًا؛ يعني أنها لم تُدخل في هذا المثال. يجب توضيح هذا عند مناقشة قائمة الدخل.

# كيف تُبنى القوائم والتقرير؟
## تجميع الأرصدة
ledger تنشئ حسابات بقيم صفر، تضيف الرصيد الافتتاحي، ثم تجمع لكل حساب المدين مطروحًا منه الدائن. الأرصدة الدائنة تكون سالبة داخليًا، ويُعكس عرضها حيث يلزم.
الأصول = النقدية + المخزون + المعدات + الحسابات المدينة. الالتزامات = الدائنون + الالتزامات الأخرى. صافي الدخل = الإيرادات - المصروفات - تكلفة البضاعة المباعة.
حقوق الملكية = رأس المال + صافي الدخل - المسحوبات. قيمة difference يجب أن تساوي صفرًا عندما نطرح الالتزامات وحقوق الملكية من الأصول.
## لماذا تظهر حسابات صفرية؟
الحسابات المدينة والالتزامات الأخرى موجودة في عرض الميزانية، لكن لا توجد عملية عامة لإدخال أرصدة لها في النسخة الحالية. تظهر صفرًا، ولا ندّعي أن كل أنواع العمليات التجارية مدعومة.
## فصل المتوقع عن المسجل
نتائج التخطيط توقعات شهرية. قائمة الدخل نتيجة العمليات التي أُدخلت، بصرف النظر عن تقديرات المبيعات. لا نجمع ربح التخطيط مرة أخرى مع دخل المحاكي؛ وإلا احتسبنا الدخل مرتين.
## التقرير
يجمع الاسم والنوع والوصف ورأس المال والمنتج والسعر والعدد والتكاليف والإيراد والربح والهامش والتعادل، ثم القوائم المسجلة. حفظ نسخة تقرير يحتفظ بصورة بيانات، والطباعة تستخدم تنسيق CSS خاصًا يخفي أدوات التنقل.
زر «تحميل PDF» يولد ثلاث صفحات A4 مباشرة على الجهاز: التخطيط، وقائمة الدخل، والميزانية. يحول عرض العربية إلى صور عالية الدقة داخل PDF حتى لا تتقطع الحروف، لكنه لا يوفر نصًا قابلًا للتحديد داخل هذه الصور. زر طباعة / حفظ PDF بديل يستخدم نافذة الجهاز.

# الحفظ المحلي والسحابي
## الزائر
localStorage يحتفظ بقائمة المشاريع تحت mizan-guest-v2. يمكن إعادة تحميل الصفحة ثم فتح المشروع. لا تنتقل هذه البيانات تلقائيًا إلى هاتف آخر، ولا تعتبر نسخة احتياطية خارج الجهاز.
sessionStorage يحتفظ بحالة جلسة الزائر وبعض اختيارات الجلسة. التفضيلات كالمظهر وشكل الأرقام محفوظة على الجهاز. نقل مشاريع الزائر إلى حساب يتم فقط بعد طلب المستخدم وتأكيد النسخ.
## الحساب
الرمز البرمجي للحساب يستخدم Supabase Auth بدل قبول كلمة مرور عشوائية. بعد نجاح الدخول يحمل user هوية المستخدم، وتُقرأ مشاريع الحساب عبر src/data.js.
جدول mizan_projects يحفظ id وuser_id وdata وrevision والتواريخ. data بصيغة JSONB لأنها تضم تكاليف وقيودًا وتقارير خاصة بمشروع واحد. هذه بنية بسيطة مناسبة للنموذج؛ التحليلات الضخمة تستفيد مستقبلًا من جداول منفصلة.
## تعارض جهازين
عند التحديث يرسل العميل رقم revision السابق ضمن شرط الطلب. إذا تغيّر المشروع في جهاز آخر، لا يتم الاستبدال صامتًا؛ تظهر رسالة إعادة الفتح. هذا تحكم تفاؤلي بالتزامن، وليس تحريرًا تعاونيًا لحظيًا.
## حالة الربط الحالية
عنوان الخدمة ومفتاحها العام مضبوطان في config.js، وauthReady مفعّل بعد اختبار التسجيل والحفظ الفعلي. نجح حفظ مشروع وعملياته وفتحه بجلسة مستقلة، ورفض التعديل بنسخة revision قديمة. الاستعادة البريدية غير مدعومة ولا تُعرض كخدمة عاملة.

# الحسابات والأمان
## الفصل بين المصادقة والتفويض
المصادقة تجيب: من المستخدم؟ تسجيل الدخول يثبت ذلك. التفويض يجيب: أي مشاريع يسمح له بقراءتها أو تعديلها؟ لا يكفي إخفاء زر أو فحص بريد المستخدم في الواجهة.
سياسات RLS على الخادم تقارن auth.uid() بعمود user_id لكل قراءة وإضافة وتعديل وحذف. التعديل يحتاج USING لاختيار الصف وWITH CHECK للتحقق من الصف بعد التغيير.
```sql
using ((select auth.uid()) = user_id)
with check ((select auth.uid()) = user_id)
```
المفتاح العام Publishable Key يجوز وضعه في الواجهة، لكنه ليس كلمة سر قاعدة البيانات ولا يمنح صلاحية إدارة. مفاتيح service_role وsecret وكلمات مرور الخدمات لا توضع في GitHub أو ملف الواجهة أو هذا الدليل.
## النصوص والجلسات
الدالة e تحول أحرف HTML الخاصة إلى كيانات عند إدخال نص المستخدم في قالب، لتقليل حقن HTML. لا توجد حاجة لتشغيل نص المستخدم ككود. بيانات جلسة الحساب يديرها SDK؛ حماية المتصفح من XSS تبقى مهمة.
اسم العرض من user_metadata يستخدم للترحيب فقط، وليس لاتخاذ قرار صلاحية. لا يوجد في المنصة تتبع سري أو ادعاء إخفاء تقني كامل للأدوات المستخدمة؛ المكتبات معروفة من المصدر.
## البريد وحدود الثقة
اختير تسجيل مباشر دون تأكيد بريد بطلب مالك المشروع لهذا العرض التعليمي. البريد معرّف فقط؛ إدخاله لا يثبت ملكيته، وقد يحجز شخص عنوان غيره. لا يوجد SMTP ولا استعادة بريدية. استخدمي بريدك واحفظي كلمة المرور، ولا تضعي بيانات حساسة أو تعتبري المنصة نظامًا إنتاجيًا معتمدًا.

# الاختبارات والنتائج المثبتة

تفرد المشاريع واستقلالها؛ المعادلات ومساهمة الوحدة؛ عدم تعديل سيناريو ماذا لو للأصل؛ التعادل الممكن وغير الممكن؛ الكميات والحدود والأرقام العشرية؛ المثال المحاسبي؛ العمليات الثماني؛ تكلفة المبيعات؛ فصل التمويل والمسحوبات؛ رفض رصيد غير كافٍ وتاريخ خاطئ؛ رفض القيد غير المتوازن.
نختبر أيضًا استعادة البيانات القديمة، والهروب من النصوص، ووجود عناصر التقرير، وحفظ مشاريع الزائر وتحديثها وإعادة فتحها وحذف واحد دون الآخر، وظهور فشل التخزين بدل ادعاء النجاح.

فُحصت رحلة التخطيط والمحاكي والقوائم وأرشيف التقرير والإعدادات بالمتصفح. تطابقت أرقام المثال، وعمل عرض الجوال 360 بكسل بلا تجاوز أفقي بالشاشات المفحوصة. حُمّل تقرير PDF فعلي من ثلاث صفحات ورُوجع بصريًا. راجعي سجل التحقق للتفاصيل وحالة نشر الرابط وتسليم الملكية.

نجاح الشكل لا يثبت صحة الحساب. اختبار الدالة وحدها لا يثبت عمل الزر. نجاح تسجيل حساب واحد لا يثبت عزل الحسابات. لذلك نحتاج اختبار وحدة، وتدفق واجهة، وحماية خادم، ونسخة منشورة.

# التشغيل والنشر والتسليم
## التشغيل من المصدر
ثبتي إصدار Node.js متوافقًا مع Vite 8، مثل إصدار 22 حديث أو أحدث. افتحي مجلد المستودع في محرر، ثم نفذي npm ci وnpm run dev، وافتحي العنوان الذي يظهر في الطرفية.
لا تفتحي index.html مباشرة بالنقر المزدوج؛ المشروع يستخدم وحدات JavaScript وبناء Vite. الأمر npm run build يولد dist، وnpm run preview يختبر النسخة المبنية محليًا.
## ما الذي ينشر؟
ملفات الإنتاج المبنية فقط للعرض: HTML وCSS وJavaScript والخطوط والشعار. المصدر محفوظ للمراجعة والتطوير. قيمة base في vite.config.js هي /mizan-sa/ لتطابق اسم المستودع في GitHub Pages.
إعداد GitHub Pages يجب أن يشير إلى ناتج البناء، لا إلى ملفات src الخام. بعد كل نشر يُفتح الرابط من جديد ويُفحص تحميل الملفات والجوال والحفظ. الحفظ المحلي مرتبط بعنوان الموقع؛ تغيير النطاق لا ينقل بيانات المتصفح القديمة تلقائيًا.
## قائمة قبل العرض
شغلي الاختبارات، افتحي رابط الإنتاج، جرّبي مشروعًا جديدًا، تأكدي من ظهور كل أزرار الجوال، جهزي PDF للتقرير، وخذي نسخة من المصدر ودليل المذاكرة. لا تعرضي كلمات مرور أو مفاتيح خدمة أو بريدًا شخصيًا على جهاز العرض.
## عند انقطاع الشبكة
قد يستمر الجزء المحمل في الذاكرة، لكن لا يوجد ضمان عمل دون إنترنت أو Service Worker في النسخة الحالية. الحفظ السحابي يحتاج اتصالًا. حددي وضع العرض بوضوح ولا تَعِدي بمزامنة لم تنجح.

GitHub وحده لا ينقل Supabase. يجب أن تملك المستلمة مشروع قاعدة البيانات أو مؤسسته. هذا التسليم الإداري لم يكتمل بعد، ولا يوجد مزود بريد لنقله في هذه النسخة. بعد الاختبار تُراجع صلاحيات الحساب السابق وتُزال؛ لا تُضاف خطة مدفوعة أو بطاقة لتجاوز حدود الخطة المجانية.
## الهوية ليست تزويرًا للتاريخ
يمكن أن تعرض المنصة اسم «ميزان» فقط دون أسماء شخصية أو علامات منصة الاستضافة السابقة. لكن نقل مستودع لا يمحو تاريخ Git أو نسب المساهمات تلقائيًا. لا ينبغي وصف النقل بأنه محو لكل أثر تاريخي.
شرح المشروع يجب أن يعكس الأدوات والمساهمات الحقيقية، مع الالتزام بسياسة المقرر بشأن المساعدة البرمجية. لا تُنسب مساهمة لطالبة لم تنفذها، ولا تُختلق قصة تطوير لإجابة سؤال المناقشة.
## قائمة تسليم
ملكية المستودع؛ رابط عامل؛ ملكية قاعدة البيانات؛ مصدر قابل للبناء؛ اختبارات ناجحة؛ دليل PDF؛ بيانات تجريبية غير شخصية؛ شرح القيود المعروفة؛ التأكد من قدرة الفريق على تحديث الموقع دون الاعتماد على حساب آخر.

«ميزان منصة تعليمية عربية تربط دراسة فكرة مشروع بالمحاسبة. نبدأ بالسعر والتكلفة، ثم نرى أثر العمليات على القوائم، بدل الاكتفاء بحفظ المعادلات.»

## الدقيقة السابعة: النتيجة والحدود
اعرضي التقرير وقولي إن القيم نتائج المدخلات، وليست توقعات سوقية مؤكدة. اشرحي أن الحساب يحفظ على الخادم، والزائر على الجهاز فقط، وأن التسجيل بلا تحقق بريد ولا استعادة بريدية. اذكري أن تسليم ملكية الخدمة مختلف عن عملها تقنيًا.
## التدريب الجماعي
تبادلن الأدوار: طالبة تعرض، وأخرى تسأل، وثالثة تغير رقمًا لتختبر فهم النتيجة. يجب أن تتمكن كل طالبة من تنفيذ السيناريو وحدها مرة واحدة على الأقل.

# أسئلة مناقشة: التصميم والبرمجة
## لماذا منصة وليست تطبيق جوال؟
للوصول برابط دون تثبيت، ولأن واجهة ويب متجاوبة تخدم الجوال والحاسوب من مصدر واحد. لا يعني هذا أن تطبيقات الجوال غير مناسبة؛ القرار يناسب نطاق المشروع وطريقة عرضه.
## هل استخدمتم React؟ وما وظيفة Vite؟
لا، التنفيذ JavaScript بوحدات مستقلة. Vite أداة تطوير وبناء، وليس مكتبة واجهات أو قاعدة بيانات. ويمكن بناء المنصة لاحقًا بإطار آخر دون تغيير فكرة الحسابات.
## لماذا SVG وخط محلي؟
SVG يظل واضحًا عند تغيير الحجم، ويُلوَّن بسهولة. الخط المحلي ضمن البناء يقلل الاعتماد على طلب خارجي لعرض العربية. لا يعني ذلك أن المنصة تعمل دون إنترنت بالكامل.
## لماذا فصل domain عن ui؟
domain يحمل منطق الحساب الخالص، وui يعرض النتائج. يمكن اختبار calculate دون فتح متصفح وتغيير الألوان دون تعديل قواعد الحساب.
## ما معنى async وawait وtry/catch؟
الطلب السحابي قد يتأخر أو يفشل. await ينتظر نتيجته داخل دالة async، وcatch يحول الفشل إلى رسالة مفهومة. لا نعلن نجاح الحفظ قبل رجوع الاستجابة الناجحة.
## لماذا لا يكفي حفظ الاسم في localStorage لتسجيل الدخول؟
لأنه لا يثبت الهوية ولا يحمي البيانات على الخادم. الحساب الحقيقي يحتاج تحققًا من كلمة المرور وجلسة وصلاحيات. وضع الزائر وظيفة مستقلة ومعلنة.

# أسئلة مناقشة: المحاسبة والأمان
## هل الربح هو رصيد النقدية؟
لا. رأس المال يزيد النقدية دون إيراد، وشراء المخزون ينقصها دون مصروف تلقائي، والشراء بالأجل يخلق التزامًا. الربح يختلف عن التدفق النقدي.
## لماذا لا تخصمون رأس المال من الربح؟
لأنه تمويل للمشروع، لا تكلفة تشغيل للفترة. نعرضه منفصلًا، ويظهر كرصيد افتتاحي في المحاكي.
## لماذا نقرّب نقطة التعادل للأعلى؟
لأن الوحدات صحيحة؛ 3.33 وحدات لا تكفي إذا كنا نبيع صورًا كاملة. عند 4 وحدات تتغطى التكاليف، بينما 3 وحدات لا تكفي.
## هل كل بيع ربح؟
لا. الإيراد ليس صافي الربح. تُطرح تكلفة البضاعة والمصروفات عند تسجيلها. إذا لم تدخل تكلفة البيع، فالنتيجة لا تشمل تكلفة مجهولة.
## هل معرفة المفتاح العام تكشف مشروعي؟
لا يمنح المفتاح العام وحده قراءة المشاريع. الجلسة وسياسات RLS تقرران الصفوف المسموحة؛ اختُبر أن حساب B لا يقرأ مشروع A ولا يعدله ولا يحذفه حتى لو عرف معرفه. المفتاح الإداري السري مختلف ولا يجوز نشره.
## كيف تمنعون ضياع تعديل جهاز آخر؟
بشرط revision عند التحديث. إذا سبق جهاز آخر بالحفظ، يفشل شرط الإصدار القديم وتظهر رسالة إعادة الفتح. لا توجد مزامنة تعاونية مباشرة في هذه النسخة.
## ماذا تقولين إذا لم تعرفي إجابة؟
حددي ما تعرفينه وما يحتاج مراجعة، وافتحي الملف أو الاختبار المسؤول. إجابة صادقة قابلة للتحقق أفضل من مصطلحات تقنية لا تصف التنفيذ.

# تمارين قصيرة مع الإجابات
## تمرين 1: مشروع رابح
الثابت 1200، والمتغير 8، والسعر 20، والعدد 150. احسبي الإيراد والمتغير والربح والتعادل والهامش قبل فتح الإجابة.
الإجابة: الإيراد 3000، المتغير 1200، الإجمالي 2400، الربح 600، التعادل 100 وحدة، والهامش 20%.
## تمرين 2: تعادل غير ممكن
الثابت 500، والسعر 10، والمتغير 12. هل زيادة المبيعات تصل إلى التعادل؟
الإجابة: لا ضمن هذه الفرضيات؛ كل وحدة تضيف خسارة مساهمة مقدارها ريالان. يجب تغيير السعر أو التكلفة، لا إظهار التعادل صفرًا.
## تمرين 3: شراء بالأجل
اشتريت مخزونًا 2000 بالأجل، ثم سددت 700 نقدًا. اكتبي القيدين وأثرهما على الدائنين.
الإجابة: مخزون مدين 2000 ودائنون دائن 2000؛ ثم دائنون مدين 700 ونقدية دائن 700. المتبقي للدائنين 1300.
## تمرين 4: تكلفة البيع
رأس المال 10000، شراء بضاعة نقدًا 2000، ثم بيع 1500 بتكلفة 900. ما الأصول والربح؟
الإجابة: النقدية 9500، المخزون 1100، الأصول 10600، الربح 600، وحقوق الملكية 10600 دون التزامات. القيد الإضافي لتكلفة البيع هو تكلفة بضاعة مباعة مدين 900 ومخزون دائن 900.
## تمرين 5: اكتشفي الخطأ البرمجي
إذا كتبنا totalCost = fixed + variableUnit فقط، فما الخطأ؟ الإجابة: أهملنا عدد الوحدات. الصحيح fixed + variableUnit * units. هذا خطأ منطقي قد لا يسبب تعطل الصفحة، لذلك تحتاج الحسابات اختبارات بقيم متوقعة.

# ملحق برمجي: تتبّع زر وحقل
## من HTML إلى JavaScript
في ui.js تنشئ button عنصرًا يحمل data-action. عند الضغط يلتقط main.js الحدث، ويبحث عن هذا الوصف. مثال مكافئ لشكل زر فتح النتائج:
```html
<button type="button" data-action="nav:results">
  النتائج
</button>
```
القيمة nav تعني التنقل، وresults اسم الشاشة. تستخدم action التقسيم عند النقطتين لتحديد الفرع. ثم تستدعي go وتُغيّر view ويُعاد render. CSS لا يقرر الحساب ولا يحفظ البيانات؛ يقرر المظهر فقط.
## قراءة النموذج
```js
const values = Object.fromEntries(new FormData(form));
const price = D.number(values.price, 'price');
const units = D.number(values.units, 'units', {
  integer: true,
  max: 10000000
});
```
FormData تجمع الحقول حسب name، لا حسب النص الظاهر بجانب الحقل. قد تعود الأرقام كنصوص؛ D.number تحولها وتتحقق منها. integer تمنع بيع 2.5 صورة في النموذج الحالي.
## id وclass وname وdata-action
id يحدد عنصرًا فريدًا مثل app أو revenue-live. class مثل panel تختار مظهر مجموعة عناصر. name مثل price يعرّف حقل النموذج. data-action وصف سلوكي يقرأه معالج الأحداث. الخلط بينها سبب شائع لعدم عمل زر أو قراءة قيمة خاطئة.

# ملحق برمجي: القيد والاختبار
## شكل القيد في البيانات
```js
const entry = {
  kind: 'buy-cash',
  amount: 3000,
  date: '2026-09-28',
  lines: [
    { account: 'inventory', debit: 3000, credit: 0 },
    { account: 'cash', debit: 0, credit: 3000 }
  ]
};
```
هذا مثال للحقول المحاسبية؛ الدالة transaction تضيف أيضًا معرفًا وعنوانًا ووصفًا ووقت إنشاء. مجموع المدين 3000 ومجموع الدائن 3000. النقدية تنخفض والمخزون يزيد، فلا يتغير إجمالي الأصول لهذه العملية وحدها.
## اختبار بسيط قابل للتشغيل
```js
import assert from 'node:assert/strict';
import { project, calculate } from './src/domain.js';
const p = { ...project(), price: 20, units: 150 };
p.costs = [
  { kind: 'fixed', amount: 1200 },
  { kind: 'variable', amount: 8 }
];
assert.equal(calculate(p).profit, 600);
assert.equal(calculate(p).breakEven, 100);
```
شغّلي المثال في ملف .mjs داخل جذر المشروع بواسطة Node.js. إذا غُيّر القانون بطريقة خاطئة يفشل assert بدل قبول نتيجة غير صحيحة. الاختبار يشرح شرطًا متوقعًا، وليس مجرد تشغيل دون رسائل خطأ.

# ملحق برمجي: التسجيل وكلمة المرور
## إنشاء الحساب والدخول
نموذج signup يجمع الاسم والبريد وكلمة المرور وتأكيدها. validatePassword يرفض عدم التطابق والطول خارج 8 إلى 128 وغياب الأحرف الإنجليزية أو الأرقام. يستدعي main.js الدالة auth.signUp، ويتأكد من وجود session قبل إعلان الدخول؛ الاسم للعرض ولا يمنح صلاحيات.
Supabase يتحقق من كلمة المرور ويخزن تجزئتها بطريقة bcrypt على خوادمه. الواجهة لا تخزن كلمة المرور داخل المشروع. يدير SDK رموز الجلسة؛ يجب عدم نشرها أو تصويرها، وهي مختلفة عن المفتاح العام المنشور.
## التغيير دون بريد
الإعدادات، ثم الملف الشخصي، ثم تغيير كلمة المرور. تدخل المستخدمة الحالية والجديدة وتأكيد الجديدة. يتحقق src/auth.js من الحالية بتسجيل دخول جديد، ثم يرسل التغيير للخادم:
```js
await connection.auth.signInWithPassword({
  email: user.email,
  password: currentPassword
});
await connection.auth.updateUser({
  password,
  current_password: currentPassword
});
```
المقتطف مختصر؛ الكود الفعلي يفحص الأخطاء والجلسة وتطابق user.id قبل التحديث وبعده. إعداد الخادم يطلب الحالية أيضًا. كلمة قديمة خاطئة لا تمر؛ وبعد نجاح التغيير تفشل القديمة وتعمل الجديدة، كما أثبت اختبار التكامل.
## ماذا إذا نسيت كلمة المرور؟
لا توجد وسيلة استعادة بريدية في هذه النسخة. لا يكفي إدخال البريد لتعيين كلمة جديدة؛ ذلك كان سيسمح بسرقة الحساب. تغيير كلمة المرور بمعرفة الحالية وظيفة مختلفة تمامًا عن الاستعادة عند فقدانها.

# التشغيل المجاني والاستعداد للمناقشة
## أين التكلفة؟
وقت إعداد النسخة: GitHub Pages مجاني للمستودع العام، ومشروع Supabase على خطة Free بقيمة صفر. لا نطاق مدفوع ولا SMTP ولا إضافات Pro. الخطة ليست بلا حدود؛ 500 MB لقاعدة البيانات و5 GB لنقل البيانات ضمن شروطها، وقد يتوقف المشروع بعد أسبوع خمول. لا توجد نسخ احتياطية تلقائية في Free.
إذا بلغ الاستخدام الحدود أو توقفت الخدمة، لا تقبلوا ترقية مدفوعة تلقائيًا. راجعوا الحالة أو أوقفوا الاستخدام السحابي واستخدموا الزائر للعرض المؤقت، مع توضيح أنه لا يسحب مشاريع السحابة تلقائيًا. سياسة الفريق الحالية: عدم دفع أي مبلغ.
## قبل يوم العرض
افتحي الرابط مبكرًا، وتحققي من تسجيل الدخول ونجاح الحفظ. إذا كان Supabase متوقفًا، يراجعه مالك الخدمة من لوحته. جهزي مثالًا اصطناعيًا في وضع الزائر ونسخة PDF للتقرير والدليل. لا تنتظري لحظة المناقشة لاكتشاف انقطاع الإنترنت.
## أسئلة حاسمة
هل المجانية تعني أن المشروع بلا خادم؟ لا؛ الواجهة على Pages والخلفية على Supabase Free. هل قاعدة البيانات انتقلت مع GitHub؟ لا، تحتاج نقلًا مستقلًا. هل البريد مؤكد؟ لا، هو معرف للحساب. هل الاختبارات تغني عن الفهم؟ لا، افتحي الاختبار واشرحي المدخل والنتيجة المتوقعة والسبب.
